# LCDD v0.6.0 Implementation Plan — Drift, Discovery, and Scoped Retrieval

**Status:** Active — PR 0 self-governance implemented
**Version:** 0.1.0
**Target Milestone:** v0.6.0
**Prerequisite:** Context Debt Gates 0–1 and PR 0 self-governance complete
**Last Updated:** 2026-08-08

---

## 1. Objective

v0.6.0 closes the largest gap in the LCDD feedback loop: the implementation can currently store,
query, validate, observe, and improve Contexts, but it cannot determine which Contexts matter to a
specific change, discover governance knowledge in the current repository, or detect when code and
Context diverge.

The milestone delivers four vertical slices in dependency order:

1. change-scoped validation;
2. task-scoped Context Bundles;
3. local repository discovery; and
4. code-to-Context drift detection.

Each slice includes Core contracts, CLI behavior, MCP exposure where appropriate, tests,
documentation, and dogfooding evidence. The target is a dependable local-first foundation, not a
hosted service, IDE extension, GitHub App, vector database, or autonomous Context mutation.

## 2. Baseline and Constraints

### 2.1 Available foundation

- `FileRegistry` provides validated file-backed Context storage and lifecycle operations.
- `ContextVerifier` performs lifecycle, scope, and enforcement checks.
- CQL provides deterministic Registry filtering and ordering.
- `RuleEngine`, `ContextNormalizer`, `ReviewManager`, and `ImproveEngine` provide the
  candidate-to-governance path.
- The CLI has integration tests; MCP has contract and stdio tests.
- Gate 1 provides argument-based process execution, verifier resource limits, confidential-source
  controls, and `npm run verify:release`.

### 2.2 Invariants

The implementation MUST preserve these constraints:

- only Active Contexts participate in enforcement and default Bundles;
- deprecated and archived Contexts MUST NOT silently enter agent Context;
- higher-authority Contexts MUST NOT be discarded to satisfy a size budget;
- code is evidence of drift, not authority to rewrite a Context;
- discovery and drift MAY create candidates or recommendations but MUST NOT activate a Context;
- Hardened Contexts MUST remain human-controlled;
- all Git operations MUST use argument-based execution and bounded output/time;
- cloud analysis MUST honor confidential-source restrictions;
- Core owns business logic; CLI and MCP remain thin adapters.

### 2.3 Dogfooding prerequisite

Before adding v0.6 feature semantics, this repository governs its own development through the
tracked `.lcdd/` Registry and `lcdd-development` Context Pack. Hardened Contexts protect normative
RFC governance, schema parity, self-hosting, and proposal-only drift behavior. Local Contexts
protect public contracts and release integrity. CI validates schema conformance, pack membership,
Hardened/Local classification, and the lifecycle audit trail.

## 3. Architecture

```text
GitChangeDetector ──► ChangeSet ──► ChangeValidator ──► ChangeValidationReport
                            │                │
                            │                └── existing ContextVerifier
                            ▼
                  ContextBundleBuilder ──► ContextBundle ──► CLI + MCP
                            ▲
                            │
RepositoryScanner ──► SourceInventory ──► Candidate Contexts ──► ReviewManager
        │
        └──────────────► DriftEngine ──► DriftReport ──► Trigger/Improve recommendation
```

New Core modules:

| Module | Responsibility |
| --- | --- |
| `git-change-detector.ts` | Resolve revisions and produce a normalized, safe `ChangeSet` |
| `change-validator.ts` | Map changes to Contexts, reuse `ContextVerifier`, aggregate a stable report |
| `context-bundle.ts` | Rank, resolve, and budget task-relevant Active Contexts |
| `repository-scanner.ts` | Collect bounded, allowlisted local source documents without following unsafe paths |
| `drift-engine.ts` | Run deterministic drift probes and aggregate evidence without mutating Contexts |
| `path-matcher.ts` | One shared implementation of `applies_to` matching for verifier, changes, bundles, and drift |

`ContextVerifier` currently owns a private glob matcher. The first refactor MUST extract this into
`path-matcher.ts`; otherwise each new slice will create subtly different scope behavior.

## 4. Shared Contracts

The contracts below are the public Core API. They MUST be exported from `@lcdd/core`, covered by
type-level or JSON fixture tests, and treated as stable within v0.6.x.

### 4.1 Change contracts

```typescript
type ChangeStatus = 'added' | 'modified' | 'deleted' | 'renamed' | 'copied' | 'untracked';

interface ChangedFile {
  path: string;
  previous_path?: string;
  status: ChangeStatus;
  binary: boolean;
}

interface ChangeSet {
  mode: 'working-tree' | 'staged' | 'range';
  base?: string;
  head?: string;
  merge_base?: string;
  files: ChangedFile[];
  warnings: string[];
}

interface FileGovernanceResult {
  file: ChangedFile;
  relevant_context_ids: string[];
  results: VerificationResult[];
  decision: 'pass' | 'warn' | 'block' | 'not-applicable' | 'not-verifiable';
}

interface ChangeValidationReport {
  schema_version: '1';
  generated_at: string;
  change_set: ChangeSet;
  files: FileGovernanceResult[];
  totals: {
    changed: number;
    checked: number;
    skipped: number;
    violations: number;
    warnings: number;
  };
  merge_decision: 'pass' | 'warn' | 'block';
}
```

Deleted and binary files have no content to run through content verifiers. They are still reported
with relevant Contexts and `not-verifiable`; file-existence or repository-level checks MAY still
produce a result.

### 4.2 Bundle contracts

```typescript
interface ContextBundleRequest {
  task: string;
  paths?: string[];
  tags?: string[];
  categories?: string[];
  max_contexts?: number;
  max_characters?: number;
}

interface ContextBundleEntry {
  context: Context;
  rank: number;
  reasons: string[];
  mandatory: boolean;
  estimated_tokens: number;
}

interface ContextBundle {
  schema_version: '1';
  task: string;
  generated_at: string;
  entries: ContextBundleEntry[];
  excluded: Array<{ context_id: string; reason: string }>;
  conflicts: Array<{ context_ids: string[]; reason: string }>;
  budget: {
    max_contexts: number;
    max_characters: number;
    used_characters: number;
    estimated_tokens: number;
    exceeded_for_mandatory_contexts: boolean;
  };
}
```

Token count in v0.6.0 is explicitly an estimate (`ceil(serialized_characters / 4)`). No model
tokenizer or embedding dependency is introduced.

### 4.3 Discovery contracts

```typescript
interface ScannedDocument {
  path: string;
  kind: 'readme' | 'documentation' | 'adr' | 'agent-instruction' | 'ci' | 'manifest' | 'config';
  sha256: string;
  size_bytes: number;
  confidential: boolean;
  changed: boolean;
}

interface SourceInventory {
  schema_version: '1';
  root: string;
  generated_at: string;
  documents: ScannedDocument[];
  skipped: Array<{ path: string; reason: string }>;
  totals: { scanned: number; changed: number; skipped: number; bytes: number };
}
```

The scanner records hashes in `.lcdd/discovery/index.json`. The index contains paths, hashes, size,
kind, and confidentiality only—not source contents.

### 4.4 Drift contracts and schema amendment

Drift probes require an explicit, reviewable representation. They MUST NOT be hidden in arbitrary
`metadata`. Before implementing the engine, submit an additive RFC change to
`specification/0012-context-schema.md` and both JSON Schema copies:

```yaml
drift:
  probes:
    - id: "auth-provider"
      type: "dependency"          # dependency | import | file | environment | pattern
      paths: ["package.json", "src/auth/**"]
      expected: ["firebase"]
      forbidden: ["@supabase/supabase-js"]
      message: "Authentication provider differs from the approved Firebase Context."
```

Core report:

```typescript
interface DriftSignal {
  probe_id: string;
  context_id: string;
  detector: string;
  status: 'aligned' | 'drift' | 'uncertain' | 'error';
  confidence: number;
  evidence: Array<{ path: string; description: string; line?: number }>;
}

interface DriftReport {
  schema_version: '1';
  generated_at: string;
  scope: { paths?: string[]; change_set?: ChangeSet };
  signals: DriftSignal[];
  totals: { aligned: number; drift: number; uncertain: number; errors: number };
  recommendation_ids: string[];
}
```

The schema amendment is backward compatible: `drift` is optional. Existing v0.5.0 Contexts remain
valid without migration.

## 5. Slice 1 — Change-Scoped Validation

### 5.1 CLI contract

```text
lcd validate --changes                 # staged + unstaged + untracked vs HEAD
lcd validate --changes --staged        # index vs HEAD
lcd validate --changes --base <ref>    # merge-base(ref, HEAD) ... HEAD
lcd validate --changes --base <ref> --head <ref>
lcd validate --changes --json
lcd validate --changes --ci            # stable summary + exit code
```

`--staged`, `--base`, and an explicit `--head` combination are validated before any Git command.
`--head` requires `--base`. The existing positional path remains valid for full validation and is
mutually exclusive with `--changes`.

### 5.2 Git semantics

- All commands use `execFileSync('git', args)` with a 10-second timeout and bounded buffer.
- Working-tree mode unions:
  - `git diff --name-status -z HEAD`;
  - `git diff --name-status -z --cached HEAD`; and
  - `git ls-files --others --exclude-standard -z`.
- Range mode resolves `git merge-base <base> <head>` and diffs `<merge-base>...<head>`.
- Name-status output is parsed using NUL separators; paths with spaces and Unicode are preserved.
- Rename/copy records retain both paths.
- Shallow clone or absent merge-base returns a structured warning and a non-zero usage/error exit,
  never silently falls back to full-repository validation.

### 5.3 Validation behavior

1. Load Active Contexts once.
2. Map each changed path with the shared path matcher.
3. Read only safe, non-binary, existing files within the project root.
4. Call `ContextVerifier.verifyAll(relevantContexts, path, content)`.
5. Derive file decision from lifecycle enforcement mode:
   `block > warn > comment/silent > pass`.
6. Emit a deterministic report sorted by path, authority descending, severity descending, then ID.
7. In `--ci`, write a Markdown table to stdout and append to `GITHUB_STEP_SUMMARY` only when that
   environment variable is present and resolves to an existing writable file.

### 5.4 Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Pass, or warnings when `--strict` is absent |
| 1 | Blocking violation, or warning under `--strict` |
| 2 | Usage, Git resolution, repository-boundary, or report-generation error |

### 5.5 Test matrix

- unit: NUL parser, status mapping, rename/copy records, deduplication, deterministic sort;
- unit: shared `applies_to` matcher parity with existing verifier fixtures;
- integration: staged, unstaged, untracked, deleted, renamed, binary, path with spaces;
- integration: explicit base/head, shallow/no merge-base, not a Git repository;
- behavior: no Active Contexts, no relevant Contexts, block/warn/comment/silent, strict mode;
- CLI: human, JSON, and CI output snapshots plus exit codes;
- security: invalid revision arguments, path traversal, output-file boundary.

### 5.6 Completion gate

- `lcd validate --changes --json` has a documented stable fixture.
- CI uses change-scoped validation on pull requests while retaining full validation as a scheduled
  or explicit job.
- No duplicate glob or enforcement implementation is introduced.

## 6. Slice 2 — Task-Scoped Context Bundle

### 6.1 Selection algorithm

Selection is deterministic and explainable:

1. Start with Active Contexts only.
2. If paths are supplied, exclude Contexts whose `applies_to` matches none of them.
3. Mark a Context mandatory when its mode is `block` and it matches a supplied path, or when its
   authority level is 4 and it matches explicit tags/categories/paths.
4. Score remaining Contexts using additive integer signals:
   - matching path: +100;
   - requested tag: +40 each;
   - requested category: +40;
   - task token in title: +20 each;
   - task token in tags: +15 each;
   - task token in description: +5 each, capped at +25;
   - authority level: `level * 10`;
   - severity: critical +25, high +20, medium +10, low +5, info +0.
5. Apply explicit `superseded_by`/`supersedes` relations. Active superseding Contexts rank before
   superseded ones; both remain visible in `excluded` reasoning.
6. Do not silently resolve equal-authority conflicts. Include both when possible and list the
   conflict; if mandatory, both may exceed budget.
7. Sort by mandatory, rank, authority, severity, updated time, then ID.
8. Apply context and character budgets to non-mandatory entries.

Common stop words and token normalization are fixed in code and tested. v0.6.0 does not use an LLM,
embedding model, or user-specific ranking history.

### 6.2 Interfaces

```text
lcd context bundle "implement password reset" --path api/auth.ts --tag security
lcd context bundle "implement password reset" --max-contexts 20 --max-characters 24000
lcd context bundle "..." --json
```

MCP adds `lcdd_get_context_for_task` with the same request fields and returns the exact Core bundle
contract. The MCP tool remains read-only.

### 6.3 Test matrix

- lifecycle filtering and deprecated/archived exclusion;
- deterministic output independent of Registry file order;
- path, tag, category, title, description, authority, and severity ranking;
- supersession and equal-authority conflict reporting;
- mandatory Context retained when the budget is too small;
- stable character and estimated-token accounting;
- empty task, no match, invalid budgets, and duplicate input paths;
- CLI JSON fixture and MCP stdio success/error contract;
- experiment fixture comparing full Registry size to Bundle size.

### 6.4 Completion gate

- Bundle output is deterministic across five repeated runs.
- No deprecated or archived Context appears in entries.
- A benchmark fixture demonstrates at least 5× size reduction for a scoped task, or the result is
  honestly recorded as not meeting the hypothesis.
- Documentation distinguishes estimated tokens from tokenizer-accurate counts.

## 7. Slice 3 — Local Repository Discovery

### 7.1 Default collection scope

Included by default:

- root `README*`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, and `SECURITY.md`;
- `docs/**/*.{md,mdx,txt}`, `adr/**/*.{md,mdx}`, and `architecture/**/*.{md,mdx}`;
- `.github/**/*.{md,yml,yaml}`;
- `package.json`, workspace manifests, `tsconfig*.json`, ESLint configuration, and selected
  environment examples such as `.env.example`;
- explicit extra globs from `.lcdd/config.yaml`.

Excluded by default:

- `.git`, `.lcdd`, dependency directories, build output, caches, generated files, lockfiles,
  minified files, binary files, secrets, and real `.env*` files;
- symlinks whose resolved target is outside the project root;
- files over 256 KiB and scans exceeding 5 MiB total content.

`.gitignore` is honored. `.lcddignore` provides stronger LCDD-specific exclusions. An ignored path
is never re-included by a broad default glob.

### 7.2 CLI stages

```text
lcd discover                         # inventory changed sources; no Context writes
lcd discover --json                  # stable SourceInventory
lcd discover --all                   # ignore prior hashes, still honor safety exclusions
lcd discover --extract              # deterministic sentence candidates
lcd discover --extract --backend ollama
lcd discover --apply-candidates      # validate, classify, save as Candidate/pending review
```

The default command is read-only. `--apply-candidates` is explicit and never implies approval or
activation.

Deterministic extraction initially selects bounded sentences containing normative language such as
MUST, MUST NOT, SHALL, SHOULD, required, prohibited, or project-specific rule markers. Every
candidate retains file path, line range, source hash, extraction method, and confidence. Optional
LLM extraction reuses `Extractor` and the Gate 1 cloud/confidentiality controls.

### 7.3 Candidate lifecycle

1. scanner produces `ScannedDocument` records;
2. extractor produces source-linked candidates;
3. normalizer validates and deduplicates;
4. candidates are saved with `lifecycle: candidate` and `review_status: pending` only when
   `--apply-candidates` is explicit;
5. `ReviewManager` owns all approval or rejection;
6. no discovery code may call an Active transition.

This intentionally differs from `lcd extract --auto`, which currently writes Draft Contexts. The
shared normalizer SHOULD gain an output-lifecycle option rather than duplicating normalization.

### 7.4 Test matrix

- default allowlist and all exclusion classes;
- `.gitignore` plus `.lcddignore` precedence;
- symlink inside root, symlink outside root, and symlink loop;
- binary detection, size caps, total cap, and invalid UTF-8;
- initial scan, unchanged scan, changed scan, removed document;
- deterministic sentence location and source-hash provenance;
- duplicate candidate across multiple documents;
- confidential file never sent to a cloud provider;
- candidate-only lifecycle and review status;
- dogfood scan of this repository with recorded false positives and omissions.

### 7.5 Completion gate

- A default scan is read-only and reproducible.
- Incremental scan reads only changed documents after the first run.
- This repository produces an inventory and a reviewed candidate report without modifying Active
  Contexts.
- False-positive and omission observations are recorded in an experiment fixture.

## 8. Slice 4 — Code-to-Context Drift

### 8.1 Delivery sequence

1. Approve the additive `drift.probes` RFC/schema change.
2. Implement the detector interface and report aggregation.
3. Implement five deterministic detectors.
4. Add change-scoped execution using `ChangeSet`.
5. Add CLI and MCP read-only surfaces.
6. Add `DRIFT_DETECTED` to `TriggerEvaluator`.
7. Add proposal-only ImproveEngine plans.
8. Add optional semantic provider only after deterministic benchmark results exist.

### 8.2 Deterministic detectors

| Detector | Evidence | Initial behavior |
| --- | --- | --- |
| dependency | package/workspace manifests | Expected dependency missing or forbidden replacement present |
| import | bounded source files | Expected import absent or forbidden import present |
| file | repository paths | Required file absent or forbidden file present |
| environment | config/example files | Expected key/value marker absent or forbidden marker present |
| pattern | scoped text files | Safe bounded regex or literal alignment check using verifier limits |

Every signal includes file evidence and confidence. Deterministic exact evidence uses confidence
1.0. Absence-based findings use at most 0.8 unless the probe defines an exhaustive scope. Parse
errors return `error`, never drift.

### 8.3 Interfaces

```text
lcd drift                         # all Active Contexts with drift probes
lcd drift --changes               # only probes affected by current ChangeSet
lcd drift --context <id>
lcd drift --json
lcd drift --strict                # drift or errors produce exit 1
```

MCP adds `lcdd_detect_drift`. It returns a report and cannot apply recommendations.

`DRIFT_DETECTED` recommendations use actions `review-clarity` or a new proposal-only
`review-drift`. The action is non-executable in v0.6.0. ImproveEngine MUST return
`requires_approval: true`; Hardened and Local Contexts both require review because code cannot
declare governance truth.

### 8.4 Required scenarios

- Firebase Context, Firebase dependency/import present: aligned.
- Firebase Context, Supabase added and Firebase removed: drift with both evidence items.
- Approved migration Context supersedes Firebase: no stale drift alert from the superseded Context.
- Both providers present during migration: uncertain, not drift.
- Dependency parser failure: error with path, no recommendation.
- Drift in Hardened Context: proposal only, no mutation path.
- Confidential files: deterministic local scan allowed; semantic cloud provider prohibited.

### 8.5 Completion gate

- The Firebase-to-Supabase fixture is detected deterministically.
- Intentional supersession suppresses the obsolete alert.
- Every drift recommendation links to evidence and remains non-executable.
- The full closed-loop diagram can truthfully mark Detect Drift as implemented for declared probes;
  docs explicitly state that undeclared semantic drift remains out of scope.

## 12. Release Gates

v0.6.0 is complete only when all gates pass:

### Functional

- all four slices meet their completion gates;
- CLI human and JSON interfaces are stable;
- MCP exposes Bundle and Drift tools through tested stdio contracts;
- no Active Context can be created by discovery or drift.

### Security

- all Git and filesystem paths remain within the project boundary;
- source/file sizes, process time, buffers, and regex execution are bounded;
- confidential sources never reach cloud providers;
- `npm audit --omit=dev` reports zero vulnerabilities.

### Evidence

- change validation is dogfooded on this repository;
- Bundle size hypothesis has a recorded result;
- discovery false positives/omissions are recorded;
- required drift scenarios are reproducible.

### Release integrity

- `npm run verify:release` passes;
- website build passes;
- reference and runtime schemas are identical;
- changelog, roadmap, package versions, MCP tool count, and public maturity statements agree;
- working tree is clean after generated artifacts are excluded.

## 13. Explicitly Deferred

The following do not belong in v0.6.0:

- GitHub App or automated PR comments;
- VS Code extension;
- hosted or database-backed Registry;
- embedding-based Bundle ranking;
- automatic semantic drift inference without declared probes;
- automatic Context modification in response to drift;
- cross-repository organization hierarchy;
- accurate model-specific tokenization;
- protocol server or marketplace.

These remain in v0.7.0+ and MUST NOT expand v0.6.0 scope.

## 14. First Implementation Step

PR 0 is implemented: the repository now has a tracked Registry, Context Pack, lifecycle history,
and CI governance check. The next implementation change is PR 1: extract the shared path matcher
and add the four public contract families. This is
the smallest change that prevents duplicated semantics across all later slices. After PR 1, build
`GitChangeDetector` and `ContextBundleBuilder` in parallel, then expose change validation before
starting discovery and drift.

The first user-visible increment should be `lcd validate --changes --json`; it has immediate CI
value, exercises the shared scope model, and produces the ChangeSet later consumed by Bundle and
Drift.
